# 数据文件说明

本目录保存网站页面使用的数据。每份数据由两个同名文件组成：`<名称>.json` 保存数据本身，`<名称>.ts` 导入 JSON、声明类型并导出读取函数。页面只通过 `.ts` 模块读取数据，不直接导入 JSON。

## 通用约定

- JSON 使用两个空格缩进，文件末尾保留一个换行。字段名使用英文驼峰，同一类记录的字段顺序保持一致，方便对比前后的差异。
- 需要按语言切换的值写成 `{ "zh": …, "en": … }`，对应 `src/i18n/index.ts` 中的 `Localized` 类型。
- 时间统一写成 UTC 的 ISO 8601 字符串，精确到秒，例如 `2025-11-18T06:35:19Z`。
- 没有值的字段写 `null`，不省略字段。可选的子列表是例外，没有内容时省略这个字段，例如更新日志中没有子条目的条目不带 `items`。
- 读取模块不在运行时校验数据。修改 JSON 之后运行 `npx astro check`，确认类型仍然匹配，再运行 `npx astro build` 确认构建成功。之后把改动推送到 `main` 分支，网站会自动发布，见项目根目录 README 的「部署」。
- 外部图片只保存原图地址，不带尺寸参数。页面展示时用 `images.ts` 的 `resizeImage` 生成缩略图地址。
- 抓取和转换数据用的脚本是一次性的，不放进项目。脚本用 Node.js 编写即可，它自带 `fetch`，不需要安装依赖。

### 访问外部网站

- 使用默认请求头，不带 Cookie，也不模仿浏览器的请求头。对同一网站的连续请求之间保持间隔，具体间隔写在各节的步骤中。
- 不访问 B 站的任何接口和页面。B 站有风控签名机制，用程序访问属于绕过平台的反爬措施，所以 B 站视频的信息只能由人提供。直接请求 `*.hdslb.com` 上的图片文件不在此列。

## 外部图片（images.ts）

`resizeImage(url, width)` 按目标宽度返回缩略图地址。`width` 是实际像素，也就是 CSS 宽度乘以设备像素比。以下规则都经过实际请求验证：

| 图片来源 | 缩略图地址 | 说明 |
|---|---|---|
| Steam（`images.steamusercontent.com`） | `<原图地址>?imw=<宽>&impolicy=Letterbox` | 缺少 `impolicy=Letterbox` 时，服务器忽略尺寸参数并返回原图。只给宽度时按原比例缩小；同时给出 `imh` 和 `letterbox=true` 会在图片四周补黑边。目标宽度大于原图时不会放大。输出总是 JPEG。 |
| B 站（`*.hdslb.com`） | `<原图地址>@<宽>w.webp` | 按原比例缩小并转为 WebP，不会放大。 |
| 其他来源 | 原图地址 | 不做处理。 |

需要按屏幕宽度和像素密度选择尺寸时，用 `resizeSrcset(url, widths)` 生成 `srcset`，再配合 `sizes` 使用。图床不支持缩放时它返回 `undefined`，图片只使用 `src`。

B 站的图片服务器按 Referer 防盗链，请求带有其他网站的 Referer 时返回 403。显示 B 站图片的 `<img>` 必须加上 `referrerpolicy="no-referrer"`。

## 模组（mod）

`mod.json` 保存模组在 Steam 创意工坊上的基本信息，大部分字段来自 Steam 的公开接口。

### 字段

| 字段 | 含义 | 来源 |
|---|---|---|
| `id` | 创意工坊物品编号 | 固定为 `3309460746` |
| `name` | 模组在 Steam 上的标题 | 接口返回的 `title` |
| `version` | 当前版本号 | 接口返回的 `description` 中，【Current Version】之后第一个 `[b]…[/b]` 里的版本号 |
| `itemCount` | 模组物品总数 | 手动维护，Steam 不提供 |
| `updatedAt` | 最后更新时间 | 接口返回的 `time_updated` |
| `subscriptions` | 当前订阅数 | 接口返回的 `subscriptions`，不是 `lifetime_subscriptions` |
| `fileSizeMb` | 文件大小，单位为 MB | 创意工坊页面 |
| `screenshots` | 截图，按页面上的顺序排列。每一项有原图地址 `image` 和原图的像素宽高 `width`、`height` | 创意工坊页面 |
| `related` | 模组简介中推荐的其他创意工坊物品，字段见下表 | 接口返回的 `description` 和各物品的详情 |

`related` 中的每一项：

| 字段 | 含义 |
|---|---|
| `id` | 创意工坊物品编号 |
| `title` | 中英文名称。英文与模组简介中的链接文字相同，中文由人填写 |
| `kind` | 卡片上的类别标签，例如「自定义游戏」，由人填写 |
| `previewUrl` | 这个物品的接口返回的 `preview_url` |

数据中只保存页面实际用到的字段，接口返回的其他字段（例如首次发布时间和收藏数）不写入。相关物品的创意工坊页面地址由 `mod.ts` 根据 `id` 生成，不保存在数据中。模组的创意工坊页面和 Steam 更新日志页面的地址是固定的站点常量，写在 `src/config/site.ts` 的 `links` 中，也不在这份数据里。

### 重新生成

1. **查询接口。** 发送下面的 POST 请求，不需要密钥。所需的字段都在返回结果的 `response.publishedfiledetails[0]` 中，按上表填写；`time_updated` 是 Unix 时间戳，单位为秒。

   ```
   curl -s -X POST https://api.steampowered.com/ISteamRemoteStorage/GetPublishedFileDetails/v1/ -d 'itemcount=1&publishedfileids[0]=3309460746'
   ```

2. **读取文件大小。** 接口不提供这个物品的实际文件大小（`file_size` 为 `"0"`），需要请求创意工坊页面 `https://steamcommunity.com/sharedfiles/filedetails/?id=3309460746&l=schinese`。页面中第一个 `div.detailsStatRight` 的内容就是文件大小，例如 `253.571 MB`，把其中的数值写入 `fileSizeMb`。这次请求与上一步之间间隔 1 秒左右。

3. **读取截图。** 同一个页面的脚本中，变量 `rgFullScreenshotURLs` 按顺序列出了全部截图，每一项的 `url` 带有尺寸参数。用正则 `^https://images\.steamusercontent\.com/ugc/\d+/[0-9A-F]+/` 截取地址的前半部分，作为 `image` 按原顺序写入 `screenshots`。宽高按「画廊」一节第 3 步的方法从文件头读取。

4. **更新相关物品。** 模组描述的【Related Mods & Custom Games】中列出了推荐的物品。用第 1 步的接口查询这些物品，`itemcount` 和 `publishedfileids` 按物品的数量填写。`result` 为 1 的物品按描述中的顺序写入 `related`；其他值表示物品已经删除或不可见，不收录。

5. **核对版本号。** `version` 应当与 `changelog.json` 第一条记录的 `version` 相同。两者不一致时，先检查更新日志里是否有还没有收录的新记录。

`itemCount` 只在团队给出新的物品总数时修改。

## 更新日志（changelog）

`changelog.json` 保存模组在创意工坊上的全部更新记录，按发布时间从新到旧排列。中文是 Steam 上的原文，只统一了排版；英文是翻译。

### 字段

每条记录包含以下字段：

| 字段 | 含义 |
|---|---|
| `id` | Steam 上这条记录的编号，以字符串保存。它的数值就是发布时间的 Unix 时间戳（秒），发布后不会改变，可以作为唯一标识 |
| `publishedAt` | 发布时间，由 `id` 换算得到 |
| `version` | 版本号，例如 `4.1.2`；无法确定时为 `null`，判断方法见「版本号」 |
| `label` | 显示在版本号旁边的简短名称，例如「修复版本 - 1」 |
| `title` | 一句话标题，概括这次更新的主要内容 |
| `sections` | 正文，由若干分组组成 |

每个分组依次展示以下内容：

| 字段 | 含义 |
|---|---|
| `heading` | 分组标题，例如「核心更新」；没有标题时为 `null` |
| `paragraphs` | 说明段落，显示在条目之前 |
| `items` | 条目列表。每个条目有 `text`；带有子条目时另有 `items`，子条目的结构与条目相同。没有子条目的条目不带 `items` 字段 |

`label`、`title`、`heading`，以及段落和条目的文字，都是中英双语的对象。

每条记录在动态页上的锚点由 `changelogAnchor(entry)` 生成，形式为 `log-<id>`。首页的社区动态通过这个锚点链接到具体的记录。

### 重新生成

1. **逐页读取。** 依次请求下面的地址，页码从 1 开始，每页最多 10 条记录，两次请求之间间隔 1 秒左右。某一页没有出现新的记录编号时停止，页码超出范围时页面中不含任何记录。`l=schinese` 只影响日期等界面文字的语言，正文始终是作者发布时的原文。

   ```
   https://steamcommunity.com/sharedfiles/filedetails/changelog/3309460746?l=schinese&p=<页码>
   ```

2. **提取记录。** 页面中的每条记录由两部分组成。`div.changelog.headline` 里是显示的时间，例如「更新于：8 月 29 日 下午 6:16」，当年的日期不写年份；紧接着的 `<p id="1788052565">` 里是正文，`id` 属性就是记录编号。正文用 `<br>` 换行，其中的 `&quot;`、`&amp;` 等 HTML 实体需要解码。

3. **核对时间。** Steam 对未登录的访问按美国太平洋时间（`America/Los_Angeles`）显示时间。把 `id` 按太平洋时间换算后，结果应当与页面显示的时间一致，精确到分钟。如果不一致，说明页面结构或编号的含义发生了变化，需要先查明原因再继续。

4. **核对总数。** 记录总数应当等于创意工坊页面上 `div.detailsStatNumChangeNotes` 里显示的「N 项改动说明」。

5. **整理和翻译。** 按下面几节拆分正文、确定版本号、写标签和标题，统一中文排版并翻译成英文。

`publishedAt` 是 UTC 时间，换算成北京时间后，日期可能与 Steam 页面上显示的不同。例如 `1788052565` 在 Steam 上显示为 8 月 29 日，按北京时间是 8 月 30 日。页面显示日期时需要明确指定时区。

需要全量重新生成时，已有记录的 `version`、`label`、`title` 和英文译文以现有数据为准，只重新处理原文发生变化的记录。

### 拆分正文

原文的写法并不统一，按下面的规则拆成分组：

1. 第一行通常是版本号加名称，例如「4.1.2 更新 修复版本 - 1」。这一行的信息由 `version` 和 `label` 表达，不放进正文。如果第一行是一句有实际内容的话，例如「修复了三个严重的漏洞!」，就保留为第一个段落；如果是一个小标题，例如「更新后需要刷新一次游戏」，就作为第一个分组的标题。
2. 以 ● 开头的行是条目，行首有缩进的 ● 是上一个条目的子条目。原文没有缩进、但内容明显是上一条的明细时，也作为子条目，例如上一条以冒号结尾，后面几行逐一列出具体的参数。
3. 不以 ● 开头、篇幅很短、以冒号结尾或者本身就是小标题的行，是分组标题，例如「更新内容：」「已知问题：」「核心更新」。「存在问题：」后面在同一行直接写出问题的，拆成标题和条目。
4. 其余的行是段落。一句话被换行拆开时，例如括号里的补充说明单独占了一行，合并成一个段落。
5. 段落出现在条目之后时，另起一个没有标题的分组。条目之间有空行、空行之后又是条目时，也另起一个没有标题的分组，以保留原文的分段。

### 版本号

第一行写了版本号的，直接使用这个版本号。例如「4.0.7BlockⅡ(3)更新日志」的版本号是 `4.0.7`，「Block Ⅱ (3)」是标签。

第一行没有版本号的，按下面的顺序判断：

1. 原文明确说明了版本变化的，以原文为准。例如 `1723731870` 写着「从4.0.1变更为4.0.1 beta版本」，由此可知首发记录 `1723709323` 的版本号是 4.0.1。
2. 前后两条记录的版本号相同时，使用这个版本号。
3. 最新的一条记录，如果它的 `id` 等于接口返回的 `time_updated`，就使用创意工坊描述中【Current Version】的版本号。
4. 其他情况一律为 `null`。版本号有时会在没有写明的更新中变化，日志中从未出现过 4.0.2 和 4.0.6，所以夹在两个不同版本之间的记录，无法判断属于哪一个。

由推断得出版本号的记录：

| 记录编号 | Steam 上显示的日期 | 版本号 | 依据 |
|---|---|---|---|
| `1788052565` | 2026 年 8 月 29 日 | 4.1.3 | 发布时是最新一条，编号等于当时接口返回的 `time_updated`，描述中的当前版本为 4.1.3 |
| `1734220472` | 2024 年 12 月 14 日 | 4.0.7 | 前后两条都是 4.0.7 |
| `1733632193` | 2024 年 12 月 7 日 | 4.0.7 | 前后两条都是 4.0.7 |
| `1723709323` | 2024 年 8 月 15 日 | 4.0.1 | 下一条写明版本由 4.0.1 改为 4.0.1 beta |

无法确定版本号、保持为 `null` 的记录：

| 记录编号 | Steam 上显示的日期 | 可能的版本 |
|---|---|---|
| `1725944698` | 2024 年 9 月 9 日 | 4.0.4 或 4.0.5 |
| `1724842975` | 2024 年 8 月 28 日 | 4.0.3 或 4.0.4 |
| `1723906852` | 2024 年 8 月 17 日 | 4.0.1 beta 或 4.0.2 |
| `1723898771` | 2024 年 8 月 17 日 | 4.0.1 beta 或 4.0.2 |

这几条只在有了新的依据时再填写，例如团队成员的确认。

### 标签与标题

`label` 的写法：

- 取原文第一行去掉版本号之后的名称。名称后面的「更新内容」「更新日志」和末尾的冒号一并去掉，例如「4.1.2 几何与视界更新内容」取「几何与视界更新」，「4.1.0（履带纪元）更新内容：」取「履带纪元」。去掉版本号之后只剩「更新内容」或「更新日志」的，就用它作为标签。
- 汉字与数字之间加空格，连字符两侧也加空格，例如「补充更新1」写作「补充更新 1」，「补充更新-4」写作「补充更新 - 4」。「BlockⅡ」写作「Block Ⅱ」。
- 第一行没有名称，或者名称不适合作为标签时，从已有的标签中选一个意思相符的，例如「更新内容」「小更新」「紧急修复」「漏洞修复」。原文中口语化的说法，例如「偷偷地更新」，同样改用「小更新」；用英文写的「fix」标为「修复」。

`title` 的写法：

- 概括这次更新中最主要的一两项内容，以原文为准，例如「新增摄影机工具与多种几何方块」「修复玩家出入房间导致模块失效的问题」。
- 语气平实，不加评价，不用「全新」「重磅」这类词，也不用感叹号。
- 中文一般不超过 20 个字。英文只有句首字母和专有名词大写，句末不加句号。

### 中文排版

中文使用原文，只做以下排版上的统一，不改动用词，可能的笔误也照原文保留：

1. 去掉行首的 ●。
2. 与汉字相邻的半角逗号、感叹号、冒号和括号改为全角，中文里的直引号改为“”，`->` 改为 `→`。
3. 汉字与英文字母、数字之间加一个空格；汉字之间，以及汉字与全角标点之间，不留空格。成员名称保持原样，例如「80老宋」。
4. mod、fov、uuid、wasd 分别写作 Mod、FOV、UUID、WASD。
5. 并列的名称或尺寸之间用顿号，例如「2x3、2x4、3x4」。
6. 条目末尾不加句号，分组标题末尾不加冒号，段落保留原有的句末标点。
7. 没有闭合的括号、括号前多余的句号这类标点错误，按书面规范修正。

### 英文翻译

- 忠实于中文原文，语气平实，不增减内容。原文含义不明确的地方按字面译出，不自行补充解释。
- 零件和工具的名称中每个实词首字母大写，例如 Track Controller。Steam 英文描述中已有的名称直接沿用，同一个零件在全文中只用一种译名。
- 条目不加句号；段落是完整的句子，带句末标点。引号使用 “ ”，数值的变化照中文写作 `22→70`。
- 成员名称保留原文，例如 thanks to 叶依风。

### 增补记录

1. **找出新记录。** 请求更新日志的第 1 页，找出 `id` 不在现有数据中的记录。如果第 1 页全是新记录，继续请求下一页，直到出现已有的编号为止。
2. **整理并加入。** 按上面几节拆分正文、确定版本号、写标签和标题、翻译成英文，然后把新记录按时间顺序加到数组开头。已有记录的 `id` 和顺序保持不变。
3. **检查已有记录。** Steam 允许作者修改已经发布的日志。发现已有记录的原文与数据不一致时，只更新这条记录的正文和译文。
4. **同步模组信息。** 同时更新 `mod.json`：`version` 改为最新记录的版本号，`updatedAt`、订阅数和文件大小按接口和页面的最新数据重新填写。
5. **核对总数。** 记录总数应当与创意工坊页面上的「N 项改动说明」一致。

## 团队（team）

`team.json` 是由团队成员名称组成的数组，数组的顺序就是页面上的显示顺序，页面上的成员人数直接取数组的长度。

- 名单取自网站设计稿中的成员名单，与旧网站 `about-team.html`（提交 `942f64d`）中的成员墙一致。旧网站没有记录成员的职责或分组，所以数据中只有名称。
- 名称在中英文页面上相同，不做翻译。
- 增加成员时，按团队指定的位置插入；没有指定位置的加到末尾。名称照团队提供的写法填写，不调整其中的空格和大小写。

## 创意工坊作品（workshop）

`workshop.json` 收录团队成员在 Steam 创意工坊发布的《废品机械师》作品，也包括成员作为合作者参与的作品。作品列表来自成员的个人创意工坊页面，作品详情来自 Steam 的公开接口，分类由人判断，只保存在这份 JSON 中。

### 字段

`categories` 是作品分类，数组的顺序就是页面上的展示顺序。

| 字段 | 含义 |
|---|---|
| `id` | 分类标识 |
| `name` | 分类的中英文名称 |

`authors` 是收录了作品的成员。

| 字段 | 含义 |
|---|---|
| `id` | 站内的成员标识。画廊数据中的同一个人使用相同的 id |
| `name` | 中英文名称。英文名称有出处时才与中文不同，例如旧网站英文版中的写法；没有出处时两者相同，不自行翻译 |
| `steamId` | Steam 账号的 SteamID64 |

`works` 是作品，按接口返回的 `time_created`（首次发布时间）从新到旧排列，时间相同时按 `id` 从大到小排列。页面直接按数组的顺序展示，所以发布时间只用于排序，不写入数据。

| 字段 | 含义 |
|---|---|
| `id` | 创意工坊的物品编号 |
| `title` | Steam 上的标题，去掉首尾空白，并把连续的空白合并成一个空格 |
| `category` | `categories` 中的 id |
| `authors` | 成员 id。上传者是成员时排在第一位，其余成员按 `authors` 数组的顺序排列 |
| `previewUrl` | 接口返回的 `preview_url`，原样保存，末尾带 `/` |

成员的个人创意工坊页面和作品页面的地址由 `workshop.ts` 分别根据 `steamId` 和作品的 `id` 生成，不保存在数据中。作品的简介和更新时间没有收录，因为页面上不展示。

### 重新生成

更新时按以下步骤重新生成全部作品，已有作品的标题和预览图也随之刷新。

1. **读取作品列表。** 对 `authors` 中的每位成员，依次请求下面的地址，页码从 1 开始，每页最多 30 件，两次请求之间间隔 1.5 秒：

   ```
   https://steamcommunity.com/profiles/<steamId>/myworkshopfiles/?appid=387990&p=<页码>&numperpage=30
   ```

   这一步依赖页面结构中的两处：

   - 作品编号写在 `id="sharedfile_<编号>"` 中，用正则 `id="sharedfile_(\d+)"` 提取，提取后去重。
   - 作品总数写在 `Showing 1-30 of 66 entries` 这样的文字中，用正则 `Showing [\d,]+-[\d,]+ of ([\d,]+) entries` 读取。请求不带 `Accept-Language` 时页面是英文；如果返回的是其他语言，需要改用对应语言的文字来匹配。

   取到的编号数量达到总数，或者某一页没有任何编号时，结束这位成员的读取。页面只列出公开的作品，其中包括这位成员作为合作者参与的作品。

2. **查询详情。** 把所有成员的编号合并去重，分批向接口发送 POST 请求。这个接口不需要密钥，每次最多查询 100 个，两次请求之间间隔 1.5 秒：

   ```
   curl -s -X POST https://api.steampowered.com/ISteamRemoteStorage/GetPublishedFileDetails/v1/ \
     -d 'itemcount=2&publishedfileids[0]=<编号>&publishedfileids[1]=<编号>'
   ```

   返回结果的 `response.publishedfiledetails` 中，`result` 为 1 的是有效作品。其他值（例如 9）表示作品已经删除或者不可见，这些作品不收录。

3. **生成记录。** 按上面的字段说明，用 `title`、`creator` 和 `preview_url` 生成每件作品，再按 `time_created`（Unix 时间戳，单位为秒）排序。`creator` 是上传者的 SteamID64，它与某位成员的 `steamId` 相同时，这位成员排在 `authors` 的第一位。

4. **分类。** 已有的作品沿用 `workshop.json` 中原来的分类，只给新作品分类，方法见下一节。

5. **写出并检查。** 写出 JSON 之后确认以下几点：每件作品的 `category` 都在 `categories` 中；每件作品的 `authors` 至少有一项；每位成员名下的作品数等于第 1 步取到的数量。最后运行 `npx astro check`。

增加成员时，在 `authors` 中添加一项。SteamID64 可以从其作品详情的 `creator` 字段得到。需要核对账号是谁时，请求 `https://steamcommunity.com/profiles/<steamId>/?xml=1`，返回内容的 `<steamID>` 元素中是这个账号当前的昵称。

按以下顺序判断，前一步已经能确定类别时，不再看后面的步骤。

1. **Steam 标签。** 接口返回的 `tags` 中有 `Tile`（地块）或 `World`（世界）的，归入「地图与建筑」；有 `Custom Game` 或 `Blocks and Parts` 的，归入「其他」。

## 画廊（gallery）

`gallery.json` 收录人工挑选的精选图片，不从任何地方自动抓取，增补和删减都由人决定。

### 字段

`artists` 是图片的作者。

| 字段 | 含义 |
|---|---|
| `id` | 作者标识。同一个人在 `workshop.json` 中已有 id 时，使用相同的 id |
| `name` | 中英文名称，规则与创意工坊作者相同 |

`items` 是图片，数组的顺序就是挑选时的顺序。

| 字段 | 含义 |
|---|---|
| `title` | 作者起的标题，没有标题时为 `null` |
| `artist` | `artists` 中的 id |
| `image` | 原图地址 |
| `width`、`height` | 原图的像素宽高，画廊排版时据此确定每张图片的比例并预留位置 |

### 增补图片

1. **整理地址。** 把 `&amp;` 还原成 `&`，把 `http://` 改成 `https://`。Steam 图片只保留正则 `^https://images\.steamusercontent\.com/ugc/\d+/[0-9A-F]+/` 匹配到的部分，去掉后面的尺寸参数；其他来源的地址不做改动。
2. **去重。** 按整理后的地址检查，已经收录的图片不再添加。
3. **读取原图宽高。** 请求时带上 `Range: bytes=0-65535`，只下载文件的前 64KB，再从文件头读取尺寸：
   - PNG：从文件开头算起，第 16 到 19 字节是宽，第 20 到 23 字节是高，都是大端整数。
   - JPEG：从第 2 字节开始逐个读取段。每段以 `0xFF` 和一个标记字节开头，之后的两个字节是段长度。遇到 SOF 段时（标记字节在 `0xC0` 到 `0xCF` 之间，`0xC4`、`0xC8`、`0xCC` 除外），从这一段的 `0xFF` 算起，偏移 5 处的两个字节是高，偏移 7 处的两个字节是宽，都是大端整数。

   前 64KB 中找不到尺寸时，再下载整个文件。连续请求之间间隔 0.3 秒。
4. **填写作者和标题。** 新作者先添加到 `artists`，再把图片放到 `items` 中合适的位置。

## 教程与视频（tutorials）

`tutorials.json` 收录与《废品机械师》有关的视频，包括教程和作品展示。视频信息不从 B 站抓取，原因见「访问外部网站」。

### 字段

`categories` 是教程库的筛选类别；`authors` 是视频作者，字段与画廊作者相同。

`videos` 中每条记录对应一个视频，同一个视频发布在多个平台时也只有一条记录。

| 字段 | 含义 |
|---|---|
| `id` | 记录的标识。视频在 B 站有来源时取 BV 号，否则取 YouTube 的视频 id |
| `title` | `zh` 是视频发布时的原标题，保持原样；`en` 是平实的意译，不带 `【戴维】` 这类频道标记和 `-废品机械师` 这类后缀 |
| `summary` | 从视频简介中摘出的有用信息，只有中文；没有可用内容时为 `null` |
| `author` | `authors` 中的 id |
| `category` | `categories` 中的 id |
| `kind` | `tutorial` 表示教程；`showcase` 表示作品展示、实况和预告，转载的官方预告片也属于这一类 |
| `featured` | 是否列在「精选教程」页和首页的视频教程区块中。精选教程页按 `categories` 的顺序排列，第一个放大显示；首页把作品展示类视频排在最前并放大显示 |
| `sources` | 视频在各平台的发布地址，至少一项，B 站排在前面 |

`sources` 中的每一项：

| 字段 | 含义 |
|---|---|
| `platform` | `bilibili` 或 `youtube` |
| `id` | B 站为 BV 号，YouTube 为视频 id |
| `url` | B 站写成 `https://www.bilibili.com/video/<BV号>`，YouTube 写成 `https://www.youtube.com/watch?v=<id>` |
| `cover` | 封面原图地址，使用 https |

页面通过 `getVideoSource(video, lang)` 选择播放来源：中文页面优先使用 B 站，英文页面优先使用 YouTube，视频只在一个平台发布时就使用那一个。

`videos` 的顺序是：官方视频在前，其余按作者分组，组内从新到旧排列。B 站视频没有可用的发布时间，新视频按这个顺序插入。

### 增补视频

1. **B 站视频。** BV 号、标题、封面地址和简介需要由人提供。`b23.tv/<BV号>` 一类的短链接改写成上面的完整地址，封面地址中的 `http://` 改成 `https://`。
2. **YouTube 视频。** 请求 `https://www.youtube.com/oembed?format=json&url=https://www.youtube.com/watch?v=<id>`，返回内容中的 `title` 是标题，`author_name` 是频道名。封面使用 `https://i.ytimg.com/vi/<id>/maxresdefault.jpg`；这个地址返回 404 时改用 `hqdefault.jpg`，它是 4:3 的图片，16:9 的视频封面上下会带黑边。
3. **多平台发布。** 同一视频发布在两个平台时，只建一条记录，`id` 取 BV 号，`sources` 中放两项。
4. **整理简介。** 只保留模组名、模组作者、素材来源和参与者署名这类信息；求点赞投币、求关注、QQ 群号和网盘链接都去掉。去掉之后没有剩余内容时写 `null`。
5. **判断类型和类别。** 先确定 `kind`，再按下表确定 `category`。展示类视频按主题归入载具、履带或武器，不属于这三个主题的归入「其他」。

   | 类别 | id | 包括 |
   |---|---|---|
   | 入门 | `beginner` | 游戏和模组的安装、基础操作、游戏设置、性能优化、蓝图的使用 |
   | 载具 | `vehicle` | 车辆、悬挂、转向、飞行器、摩托车、悬浮 |
   | 履带 | `track` | 履带，以及坦克的差速转向 |
   | 武器 | `weapon` | 武器 |
   | 进阶 | `advanced` | 逻辑电路、各种机构、空间锚、自动化、建造工具、原版技巧 |
   | 其他 | `other` | 不属于以上类别的内容 |

6. **收录范围。** 与《废品机械师》无关的视频不收录。

### 注意事项

- 两条官方视频同时发布在 B 站和 YouTube，它们的中文标题取自 YouTube 原标题中的中文部分，可能与 B 站上的标题不完全相同。
- B 站封面在页面上显示时必须带 `referrerpolicy="no-referrer"`。

## 常见问题（faq）

`faq.json` 是由问题分组组成的数组，内容由人维护。

| 字段 | 含义 |
|---|---|
| 分组的 `id`、`title` | 分组标识，以及分组的中英文标题 |
| 问题的 `id` | 页面锚点使用的标识。发布后不再修改，以免外部链接失效 |
| `question`、`answer` | 中英文的问题和答案，每个答案是一个段落 |
| `featured` | 是否同时列在首页的常见问题区块中 |

编写和修改时注意以下几点：

- 答案中不写模组的具体版本号，以免模组更新之后内容过时。
- 「遇到问题去哪里求助？」的答案中写有 QQ 群号，`src/config/site.ts` 的 `qqGroups` 中也有一份，修改群号时两处一起改。
- 中文称「传奇模组」，英文称「New Legend Mod」，上下文已经明确时英文称「the Mod」。答案中提到的页面名称与 `src/i18n/ui.ts` 中的导航文字保持一致。
- 措辞平实，只陈述事实，不夸大。英文要忠实于中文，不增删内容。
